# Итоговый аудит исследовательских находок

Дата аудита: 6 ноября 2026 года.  
Область: ссылки и технологии, собранные в `docs/Research/` и обсуждённые в текущем цикле.

## Главный вывод
Находки полезны, но относятся к разным слоям. Не превращать каталог в список обязательных зависимостей. Сначала улучшить инженерный процесс, затем провести небольшие изолированные прототипы. Jarvis должен оставаться локальным Android-приложением с локальной моделью; облачные coding agents — внешние инструменты разработки, а не runtime-зависимости приложения.

## Приоритет A — применить в процессе разработки

### 1. Superpowers
Источник: https://github.com/obra/superpowers  
Роль: методология работы coding agents — уточнение требований, проектирование, план, изолированная рабочая копия, TDD, code review и проверка перед завершением. Наиболее прямое соответствие нашим повторяющимся проблемам со сборками и незапланированными правками.
Рекомендация: первым проверить на небольшой задаче в отдельном worktree/ветке. Не давать агенту самостоятельно merge/релизить. Сохранять пользовательские правила: не плодить ветки, не удалять архивные ветки, атомарные изменения, тесты, rollback и обязательная проверка APK.
Официальные материалы: https://github.com/obra/superpowers/blob/main/README.md

### 2. OpenSpec
Источник: https://openspec.dev/  
Роль: спецификация изменения до реализации; требования, сценарии, дизайн и задачи. Особенно полезен для FamilyCore и Kingdoms, где важно не терять согласованные детали UI и геймплея.
Рекомендация: сравнить с Superpowers на одной задаче. Не внедрять оба процесса одновременно без необходимости — возможное дублирование документов и церемоний.

### 3. Gemini CLI
Источник: https://thecode.media/gemini-cli-ustanovka-nastrojka-claude-code/  
Роль: альтернативный coding agent для исследования, ревью diff и запуска тестов. Это облачный модельный доступ, не локальная модель Android.
Рекомендация: сначала проверить актуальные условия Google API, цену и квоты. Использовать как дополнительного ревьюера, а не как обязательную часть CI. Не полагаться на старые сведения статьи о бесплатной/потребительской авторизации без повторной проверки.

## Приоритет B — прототип для конкретного проекта

### 4. Nakama — Kingdoms: Crusader
Источник: https://heroiclabs.com/nakama/  
Роль: игровой backend: авторизация, матчи, realtime, matchmaking, чаты, группы, рейтинги и серверная логика.
Рекомендация: самый сильный кандидат из всех ссылок для Kingdoms. Сделать отдельный proof-of-concept: вход игрока → создание комнаты/матча → серверная проверка одного игрового действия → сохранение состояния. Для экономики, ресурсов, армии и исходов осад использовать authoritative server logic. До выбора оценить хостинг, стоимость, нагрузку, миграции, резервные копии и безопасность.
Не считать заменой игровому движку или готовой MMO.

### 5. Docling + RAGFlow / PageIndex — Jarvis
Источники:
- https://github.com/docling-project/docling
- https://github.com/infiniflow/ragflow
- https://github.com/VectifyAI/PageIndex
Роль: Docling — разбор документов; RAGFlow и PageIndex — варианты поиска и извлечения сведений из большой базы знаний.
Рекомендация: сначала проверить Docling на нескольких реальных PDF/DOCX, затем сравнить два способа поиска на одном тестовом наборе вопросов. RAGFlow может быть тяжёлым для телефона; рассматривать его как отдельный серверный/настольный сервис, а не как встроенный Android runtime. Проверить, что именно можно выполнять локально и какие компоненты требуют сервера.

### 6. Mem0 — память Jarvis
Источник: https://github.com/mem0ai/mem0  
Роль: слой долговременной памяти.
Рекомендация: сравнить с собственной моделью памяти по точности извлечения, удалению/исправлению данных, приватности, размеру и офлайн-работе. Не подключать до определения политики памяти и пользовательского контроля. Сам факт open source не означает, что вся функциональность автономна на Android.

### 7. Daytona — песочницы для coding agents
Источник: https://github.com/daytonaio/daytona  
Роль: изоляция выполнения команд и кода агентами.
Рекомендация: изучить после выбора coding agent; для нашего GitHub Actions процесса может оказаться избыточным. Важна сама идея изоляции и ограничения прав.

## Приоритет C — справочные идеи, не внедрять сейчас

### 8. OutWiker
Источник: https://opennet.ru/opennews/art.shtml?num=66349  
Полезные идеи: файловая структура заметок, вложения, теги и плагины. Для текущей исследовательской базы достаточно Markdown в Git; отдельное приложение пока не требуется.

### 9. git-bug
Источник: https://github.com/git-bug/git-bug  
Распределённые задачи поверх Git. Пока GitHub Issues/PR и Actions уже обеспечивают рабочий контур. Вернуться к сравнению только если появится реальная потребность в offline-first issue tracker.

### 10. Android + ESP32-S3
Источник: https://xakep.ru/2026/09/08/android-farm-esp32/  
Возможная идея: лабораторный стенд управления собственными Android-устройствами через BLE и координатор. Не относится к текущей архитектуре Jarvis; изучать только при появлении задачи массового тестирования устройств. Не переносить сценарии ботофермы и автоматизации сторонних сервисов.

### 11. Moxnox OS
Источник: https://www.opennet.ru/opennews/art.shtml?num=66552  
Интересный самостоятельный ARM/POSIX-проект и пример self-hosting. Практической зависимости для Android-приложений нет; оставить как технический материал.

### 12. Orion browser
Источник: https://www.opennet.ru/opennews/art.shtml?num=66403  
Полезный кейс передачи open-source проекта сообществу. Главный урок — оценивать сопровождение, безопасность и жизненный цикл зависимости, а не только функции. Не связан напрямую с нашими текущими задачами.

### 13. Ubuntu proposed / security update cadence
Источники:
- https://opennet.ru/opennews/art.shtml?num=66335
- https://ubuntu.com/project/docs/how-ubuntu-is-made/concepts/package-archive/#proposed
Идея: разделить экспериментальные, beta и stable обновления; перед stable проверять регрессии и иметь rollback. Для Jarvis это принцип процесса релизов, а не готовая Android-технология. Не переносить буквально Ubuntu pockets.

### 14. Supabase, Meilisearch, ClickHouse, n8n, Frigate, OpenClaw, LocalAI, PrivateGPT, Goose, LangGraph, CrewAI, Headroom, Firecrawl
Источники и краткие описания собраны в `006-habr-100-ai-github-repositories.md`. Пока это вторичный список кандидатов. Не добавлять в проекты без конкретного сценария, проверки лицензии, требований, безопасности и стоимости. Supabase не является автоматической заменой authoritative backend Nakama; Frigate — отдельное направление умного дома, не обязательная часть FamilyCore.

## Предлагаемый порядок дальнейшей работы

1. **Инженерный процесс:** испытать Superpowers на одной небольшой задаче с чистой базовой сборкой, отдельной рабочей областью, тестами и обязательной проверкой diff.
2. **Спецификации:** попробовать OpenSpec на одной будущей функции FamilyCore или Kingdoms; сравнить пользу с обычным коротким design/implementation plan.
3. **Kingdoms:** отдельный Nakama prototype, не вмешиваясь в текущий игровой клиент до подтверждения результата.
4. **Jarvis knowledge base:** тест Docling на нескольких документах; затем сравнение RAGFlow и PageIndex на фиксированном наборе вопросов.
5. **Jarvis memory:** только после определения требований к приватности, исправлению и удалению памяти — сравнить Mem0 с текущим решением.
6. **Периодическая переоценка:** проверять активность репозиториев, релизы, лицензии, уязвимости и стоимость перед каждым внедрением.

## Обязательные правила для всех проектов
- Не внедрять технологию только потому, что она популярна или упомянута в статье.
- Сначала формулировать проблему, критерии успеха и ограничения.
- До правок фиксировать исходное состояние Git и подтверждённую базовую сборку.
- Маленькие атомарные изменения; не смешивать рефакторинг и функциональные изменения.
- Сборка и тесты должны подтверждать результат; зелёный статус Actions и доступный APK проверять отдельно.
- Не давать агентам неограниченный доступ к секретам, удалённым операциям, merge и релизам.
- Для Android Jarvis не подменять локальный inference облачным API без отдельного решения пользователя.
- Сохранять историю, логи, rollback и возможность продолжить с последней подтверждённой точки.

## Статус
Аудит — рекомендация по дальнейшему изучению, а не утверждение о внедрении. Никакие зависимости, исходный код, workflow или настройки сборки не менялись.
