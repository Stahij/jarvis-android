# Этап 4: интерфейс (часть 1), загрузка, манифест, персоны

Пояснения к коду этапа. Сам код лежит в архиве `jarvis-stage4-repo-drop.zip`, пути внутри архива совпадают с репозиторием.

**Важно:** код этапа 4 не компилировался и не запускался на телефоне. Логика двух новых модулей проверена зеркальным расчётом на Python, Kotlin-тесты подготовлены, но в проекте ещё не подключены (нужна строка в `build.gradle.kts`, см. `tests/kotlin/README.md`).

## Что вошло

### 1. Оформление ответов: `MessageFormatter.kt` (новый)
Делит ответ модели на текст и блоки кода (```lang ... ```).
- Незакрытый блок кода считается кодом до конца текста. Это важно при стриминге: пока ответ печатается, незакрытая кодовая часть не превращается в обычный текст.
- Имя языка проходит проверку (латиница, цифры, `+ . # _ -`, до 20 символов). Иначе тег отбрасывается, чтобы в подписи не попало что-то из текста модели.
- `speakableText` возвращает только текст без кода для озвучки.

В `MainActivity` добавлены `renderFormatted` и `buildCodeBlock`: блок кода выводится на тёмном фоне с моноширинным шрифтом, горизонтальной прокруткой и кнопкой «копировать». Пока ответ печатается, поток идёт в обычный `TextView`, как и раньше. Замена на оформленные блоки происходит один раз, когда ответ готов (`handleReply`). Это сознательно: переразбирать текст на каждом токене дорого и мерцает.

### 2. Онбординг загрузки модели: `DownloadPreflight.kt` и `DeviceNetwork.kt`
Перед скачиванием 1,9 ГБ проверяется:
- **Сеть:** нет сети — понятное сообщение, загрузка не стартует.
- **Мобильный интернет:** диалог «Скачать через мобильный интернет?», ответ «Позже» ничего не скачивает. Wi-Fi и Ethernet проходят без вопросов.
- **Место:** нужно (оставшийся объём модели + 300 МБ запаса). Уже скачанный `.part` уменьшает требование. Если места мало, выводится, сколько нужно и сколько свободно.

Место меряется по `filesDir`, а не по папке модели: папка может ещё не существовать, а раздел тот же. Если `StatFs` упал, загрузка не блокируется (`Long.MAX_VALUE`), реальная защита остаётся на проверках размера и GGUF-заголовка после скачивания.

`downloadQwenModel()` стала проверкой, а прежнее тело переехало в `startQwenDownload()` без изменений.

### 3. Персоны: `Personas.kt` и `assets/personas.json` (новые)
Тексты персон вынесены из `MainActivity` в JSON, который лежит в `assets`. Встроенные тексты в коде остаются запасным вариантом: если файла нет или он сломан, приложение работает как раньше. Пустые значения и неизвестные ключи игнорируются.

Честно о словах «редактируемый JSON»: файл правится в репозитории без правки Kotlin, но в APK он попадает при сборке. Чтобы поменять персону на телефоне, нужна пересборка и установка.

### 4. Манифест
- Убрано `RECORD_AUDIO`. Проверено поиском по коду: в рантайме разрешение не запрашивается, голосовой ввод идёт через системный `RecognizerIntent`. Если голосовой ввод перестанет работать на каком-то устройстве, это первое место для проверки (чек-лист, пункт 34).
- `usesCleartextTraffic="false"`: в коде нет ни одного `http://` адреса, всё идёт по HTTPS.
- `allowBackup="false"`: ключ GitHub хранится в Keystore и при восстановлении из бэкапа всё равно не расшифруется. Отключать бэкап значит не терять этого вопроса вообще.
- `BootReceiver` с `exported="false"`: системный `BOOT_COMPLETED` доставляется и без `exported=true`. Это проверяется на устройстве (пункт 35), потому что у некоторых прошивок с этим бывают сюрпризы.
- Добавлено `ACCESS_NETWORK_STATE` для проверки сети.

### 5. Тесты (подготовлены, не подключены)
- `MessageFormatterTest`: обычный текст, код с языком, незакрытый блок, небезопасный тег, озвучка без кода, пустой ввод.
- `DownloadPreflightTest`: Wi-Fi, офлайн, мобильная сеть с подтверждением и без, мало места, частично скачанный файл, форматирование.
- `PersonasTest`: переопределение и игнорирование пустых значений, наличие встроенного текста для каждой персоны.

Подключение описано в `tests/kotlin/README.md`: одна зависимость JUnit и одна `org.json` для JVM-тестов.

## Что НЕ сделано в этапе 4 и почему

- **Compose + Material 3 и разбиение `MainActivity` на экраны.** Это самая большая переделка в плане, а я не могу собрать проект. Переписывать UI вслепую с большим числом ошибок хуже, чем не переписывать. Предлагаю делать этап 4b после первой успешной сборки и проверки этапов 1–4 на телефоне.
- **Тёмная и светлая тема, `strings.xml`, `contentDescription`.** Требуют того же переписывания разметки, поэтому идут вместе с 4b.
- **Один экран настроек вместо диалогов из меню.** Тот же случай.
- **Орб: быстрый ввод, поворот, insets, своя иконка уведомления.** Отдельная задача, не начата.
- **Озвучка по предложениям во время генерации.** Нужна очередь TTS с разбиением по границам предложений; сейчас озвучивается только готовый ответ.
- **«Повторить» и индикатор ток/с в пузыре.** Данные для индикатора уже пишутся в диагностику, но вывода в UI нет.
- **`network_security_config`.** Поскольку cleartext выключен, файл не нужен; его добавят, если понадобится разрешить http для конкретного домена.

## Риски при первой сборке (что смотреть в первую очередь)

1. `MainActivity.kt`: `renderFormatted` вызывается из `addBubble` до добавления кнопок действий. Если порядок детей в пузыре окажется другим, блоки кода могут появиться не на месте. Проверить на пунктах 27–30.
2. `handleReply`: ищет родителя `body` через `body.parent`. Если пузырь к этому моменту уже удалён (например, ошибка без текста), ветка уходит в `body.text = ...` и ничего не ломает.
3. Кнопка ▶ берёт текст из `bubble.tag`. У старых пузырей тега нет, тогда используется `body.text` (как раньше).
4. `DeviceNetwork.current`: на некоторых прошивках активная сеть VPN показывается как `OTHER`, и мобильный вопрос не появится. Это безопасная сторона: загрузка просто идёт без вопроса.
